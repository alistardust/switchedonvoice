# Phase 23: Singing Exercise Library - Context

**Gathered:** 2026-05-30
**Status:** Ready for planning

<domain>
## Phase Goal

Phase 23 turns the singing feature set into a structured practice library by
adding warm-up scales, arpeggios, and interval drills that use contour-based
visuals instead of staff notation, while feeding progression and personal bests.
</domain>

<dependencies>
## Dependencies on Earlier Phases

- **Phase 21:** Singing mode, target ranges, and health reminders already exist.
- **Phase 22:** Melody content loading, prepared note-bar rendering, singing
  attempt persistence, and the top-level Singing tab already exist and should
  be reused rather than forked.
- **Phase 6/7:** `CurriculumService`, skill IDs, and the skill-tree UI already
  exist. Singing exercises should become another curriculum-backed source of XP
  and unlock state.
- **Phase 11/14:** `ArcadeRepository` personal-best/history semantics and XP
  Breakdown grouping already exist; exercise completion should plug into the
  same progress surfaces via stable namespaced score IDs.
- **Existing UI seam:** `src/switchedonvoice/ui/singing_panel.py` from Phase 22
  becomes the home for multiple singing content types (melodies + exercises).
</dependencies>

<decisions>
## Key Decisions

- **D-23-01:** Store canonical exercises as relative contour definitions
  (scale-degree or semitone offsets plus duration units), not as duplicated
  absolute-Hz note lists. Range variants are generated by transposition at load
  time.
- **D-23-02:** Keep range variants explicit in metadata after generation.
  Every playable exercise instance needs a stable `exercise_slug` and
  `range_slug` so personal bests, XP events, and filters remain deterministic.
- **D-23-03:** Reuse the Phase 22 note-target renderer for exercise playback.
  Exercises should appear as pitch contour bars/curves, not music notation.
- **D-23-04:** Extend the Singing tab with an Exercise browser/filter view
  instead of creating another top-level tab. Users should browse melodies and
  exercises in one singing-focused surface.
- **D-23-05:** Add a new curriculum category, `Singing`, with three planned
  skill families: `Pitch Range`, `Vibrato`, and `Breath Control`. The mapping
  from exercise completions to skill unlocks belongs in curriculum seed/service
  data, not hard-coded widget logic.
- **D-23-06:** Personal-best tracking uses namespaced score IDs such as
  `exercise/<exercise-slug>/<range-slug>`. That keeps contralto, mezzo, and
  soprano results independent without requiring a second PB system.
- **D-23-07:** Phase 23 should reuse the generic `singing_attempts` tables from
  Phase 22 with `content_type = "exercise"`. No parallel exercise-specific
  attempt table is needed unless later coaching phases require extra detail.
</decisions>

<research>
## Research Findings

- **R-23-01:** Relative contour definitions are easier to transpose, review,
  and test than absolute note lists. A chromatic scale defined as semitone
  offsets `[0, 1, 2, ...]` can generate every range variant without duplicated
  JSON.
- **R-23-02:** Range filtering is cheapest when the generated exercise metadata
  carries normalized fields (`range_slug`, `exercise_type`, `difficulty`) that
  the UI can filter without rescoring or reparsing content.
- **R-23-03:** Unlock rules are more maintainable when exercise completions emit
  stable `source_type/source_id` pairs into `CurriculumService`; the skill tree
  can then react through existing progression queries.
- **R-23-04:** Personal-best independence by range variant requires the score
  namespace to include the range. Otherwise a soprano score overwrites the
  contralto score for the same base exercise.
- **R-23-05:** Optional labels (numbers or solfège) should be presentation-only.
  They must not be required for comprehension because the requirement explicitly
  says the exercises should not require musical reading ability.
- **R-23-06:** Exercise-browser performance stays simple if filters operate on
  pre-generated dataclasses instead of rebuilding transposed contours on every
  combobox change.
</research>

<data_model>
## Data Model

### Bundled exercise asset schema

```json
{
  "slug": "chromatic-ascend-descend",
  "title": "Chromatic Ascend / Descend",
  "exercise_type": "scale",
  "difficulty": "entry",
  "base_start_hz": 220.0,
  "contour_steps": [0, 1, 2, 3, 4, 3, 2, 1, 0],
  "step_duration_ms": 600,
  "optional_labels": ["1", "#1", "2", "#2", "3", "#2", "2", "#1", "1"]
}
```

### Generated runtime dataclasses

- `ExerciseDefinition`
- `ExerciseVariant`
  - `exercise_slug: str`
  - `range_slug: str`
  - `title: str`
  - `exercise_type: str`
  - `difficulty: str`
  - `notes: tuple[MelodyNote, ...]`
- `ExerciseFilter`
- `ExerciseCompletionSummary`

### Persistence reuse

Phase 23 should reuse `singing_attempts` / `singing_segment_scores` from Phase 22:
- `content_type = "exercise"`
- `content_slug = "<exercise-slug>/<range-slug>"` or separate slug fields in the
  summary dataclass before persistence

XP / PB integration should mirror each completion into:
- `ArcadeRepository` game key: `exercise/<exercise-slug>/<range-slug>`
- `CurriculumService.award_xp(..., source_type="exercise", source_id="<exercise-slug>/<range-slug>")`

### Curriculum additions

Phase 6 seed/service data should gain:
- category: `singing`
- tiered nodes for `pitch_range`, `vibrato`, `breath_control`
- unlock mapping from entry/intermediate/advanced exercises to those nodes
</data_model>

<pitfalls>
## Pitfalls to Avoid

- Do **not** duplicate 3x exercise JSON for soprano/mezzo/contralto unless the
  contour actually differs. Generate variants from one canonical source.
- Do **not** let the browser filter by interrogating the DB on every click;
  the content library should already contain enough metadata.
- Do **not** put skill-tree unlock logic inside Qt widgets. Widgets display the
  result; `CurriculumService` decides the unlock state.
- Do **not** reuse a single personal-best key for all range variants.
</pitfalls>
